# Engine gateway

## Context

Screens reach the instance's engine through one interface, `EngineGateway` (`client/src/engine/gateway.ts`): one namespace per domain (status, scenes, workflows, commands, …), each a set of React hooks. `useEngineGateway()` returns the gateway the app booted with, and the hooks in `client/src/engine/hooks/` wrap its members for components.

There are two implementations:

- **Convex** (`client/src/engine/convex/`): its reads subscribe to the Convex functions that mirror engine state, and its requests call the Convex actions that relay to the engine. The app boots with it.
- **Direct** (`client/src/engine/direct/`, `createDirectEngineGateway`): it talks to one engine over a capnweb session with no Convex in between, for the desktop app running its own engine. Reads are cached in one TanStack Query client and refreshed by the engine's event stream; requests call the engine's methods. The dashboard's own records that Convex keeps beside the engine (page intros, the dashboard's layout and notes, the macro pad, stream info presets, the go-live checklist's dismissals) it keeps in the engine's local UI settings (`direct/ui-settings.ts`), and state that must outlive the page without being the engine's (the go-live stream start marker) it asks of the desktop host it is built with (`DesktopHostState`, `client/src/engine/desktop-host.ts`). Members whose data only Convex keeps (module OAuth, the marketplace's quotes, entitlements and checkout, setup imports, starter packs, the shoutout queue and pin history) throw or reject with `GatewayUnsupportedError`, naming the member, rather than answering empty.

## Decision

The interface and its types (`client/src/engine/types.ts`) describe the engine's data as the UI uses it, and name no backend:

- **Ids are branded strings.** `InstanceId`, `ModuleId`, `MacroId`, `SceneId` and `WebhookEventId` are opaque ids issued by a gateway. Branding stops one kind of id, or a backend's own id type, being passed where another is expected.
- **Payloads are declared, not derived.** A result type is the engine's own type from `@woofx3/api` when that is what the UI reads (`EngineInfo`, `ObsStatus`, `WidgetThemes`), and otherwise a UI domain type declared in `types.ts`. Nothing there is `Doc<…>`, `Id<…>`, `FunctionReturnType<…>` or imported from `convex/`.
- **Each implementation maps at its edge.** The Convex adapter turns rows and action results into the domain types with named functions (`toSceneRecord`, `toEngineAlert`, `toWorkflowCatalog`, …) that build the domain record field by field rather than copying the row and dropping what it should not carry. Convex's own fields (`_id`, `_creationTime`, the row's `instanceId`) do not cross; where a screen needs a row's identity it gets a named field such as `id`. List reads are mapped under `useMemo`, so a mapped result keeps its identity until the Convex result changes.
- **Calls carry no instance.** An engine is single-tenant, and a gateway that talks to an engine directly talks to exactly one, so no member takes an instance id. A gateway acts on the instance its engine scope holds. The boot wiring in `client/src/engine/boot/` picks the gateway once, at the root (`EngineGatewayProvider` in `client/src/engine/context.tsx`), and sets the scope (`EngineScopeProvider`, `client/src/engine/scope.tsx`): the hosted app's `InstanceEngineScope` holds the selected instance around the app shell and the setup wizard, and the desktop app's local mode (`boot/local.tsx`) mounts the direct gateway with a scope that always holds its one engine, and the Convex adapter reads it in `client/src/engine/convex/scope.ts` to fill in the `instanceId` its Convex functions take. While the scope has no instance, reads stay loading, requests reject with `NoInstanceSelectedError`, and live subscriptions throw. A request function keeps its identity until the scope's instance changes, so an effect that depends on it runs again for a newly selected instance. The one member that names its target is the connection test, which pings an engine by URL before any instance exists. A read a caller may not want yet takes `ReadOptions` (`{ enabled: false }` skips it) rather than a null id.
- **Ids convert at the edge too.** `client/src/engine/convex/ids.ts` converts between the gateway ids and Convex document ids (`toInstanceId`, `fromInstanceId`, …), and only the adapter and the boot wiring (`client/src/engine/context.tsx`) use it. Screens and engine hooks that need the current instance for themselves (a cache key, a guard) read `useEngineScope().instanceId`; they never hand it to the gateway.
- **Cloud-only features convert in one place.** A macro's remote trigger URL is Convex's own feature, keyed by Convex ids. Where such a feature names a gateway record (a macro's trigger), it converts through `client/src/lib/cloud-ids.ts`. A gateway without Convex has none of these features.
- **Flows are states, not URLs.** Where the engine's work needs the streamer somewhere else, a member models what the UI follows rather than where the browser goes. Linking Twitch (`twitchLink.useLinkFlow`) is an attempt whose state is `starting`, `redirecting` (the Convex adapter sends the browser to Twitch's OAuth page) or `awaitingApproval` with a code to type on any device (the engine's device login, behind its `twitch.deviceLogin` capability), plus `start`, `cancel` and an unlink request; the link itself is a read. Connecting a module's OAuth integration (`moduleOAuth`), the overlay URLs (`overlays`) and the go-live checklist's overlay facts (`goLive.useOverlays`, whose `featuredUrl` is the URL to offer for OBS) answer with what the screen needs, never with a backend's own key to build a URL from.
- **Twitch channel calls are engine operations.** Ad breaks, moderation, pins, shoutouts, chat, clips, stream info and the go-live checklist each have a namespace. An engine with a `twitch.*` capability makes the Helix call itself and answers with Twitch's own body, so these types are the parsed records the widgets read (`AdSchedule`, `ChatSettings`, `StreamInfo`), never Helix bodies or a token. The Convex adapter calls the Convex actions that choose between the engine and Helix, and reads the records the dashboard keeps beside them (pin history, the shoutout queue, stream info presets, checklist dismissals); the direct adapter reads the presets and dismissals from the engine's local UI settings.
- **The live transport is the adapter's.** `client/src/lib/transport` is the Convex gateway's realtime half: it opens the engine socket with the credentials Convex recorded. The app shell keeps it connected through `session.useLiveConnection`, and widgets subscribe through `eventLog.useStreamEventsSubscription`.

`client/src/engine/boundary.test.ts` holds both sides of the line: files in `client/src/engine/` outside `convex/` may not import Convex modules or name Convex's generated types, and only `context.tsx` among them may import the adapter or `useInstance`; files outside `client/src/engine/` may not import the adapter, except `lib/cloud-ids.ts`, and may not call the Convex functions a gateway namespace owns (`namespaces.ts`). Only the Convex adapter may import `lib/transport`, or import a Convex module a namespace owns whole, types included; a screen takes those types from `client/src/engine/types.ts`.

## Consequences

- A new gateway member gets a domain type in `types.ts` first, then a mapping in the Convex adapter. The adapter objects are typed as the namespace interfaces (`convexScenesGateway: ScenesGateway`) and each mapper names every field it copies, so a Convex column that changes type or goes away fails the type check, and a new column stays behind until its domain type gains it.
- Records are keyed by what the engine knows them by (`engineCommandId`, `engineWorkflowId`, `canonicalId`) wherever one exists.
- A caller that shows a rejection's text reads `Error.message`. The Convex adapter rethrows a `ConvexError` carrying text as a plain `Error` where a caller does this (the capabilities request), so callers never depend on `ConvexError`.
